## Forward HTTP headers to subgraphs

Forwarding specific client headers (request headers) to your subgraphs is a straightforward process. By default, no headers are forwarded for security reasons. To enable header forwarding, insert the following snippet into your [config.yaml](/router/configuration#config-file) file and adjust it according to your needs.

```yaml
# config.yaml

# See https://cosmo-docs.wundergraph.com/router/configuration#config-file
# for the full list of configuration options.

headers:
  all: # Header rules for all subgraph requests.
    request:
      - op: "propagate"            # Forward a client header
        named: X-Test-Header       # Exact match (Use the canonicalized version)

      # Regex match (Case insensitive)
      - op: "propagate"
        matching: (?i)^X-Custom-.*

      - op: "propagate"
        matching: ^(Header-1|Key)$
        negate_match: true         # Ensure that all headers except the Header-1 and Key are propagated

      # Sets the value when the header was not set
      - op: "propagate"
        named: "X-User-Id"
        default: "123"

      # Rewrites the header from X-Test-1 to X-Test
      - op: "propagate"
        named: "X-Test-1"
        rename: "X-Test"

      - op: "set"
        name: "X-Custom-Header"
        value: "my-required-key"

      # Dynamic value using template expression
      - op: "set"
        name: "X-User-ID"
        expression: "request.auth.isAuthenticated ? request.auth.claims.sub : ''"

      # Source the value from a file (re-read on the configured interval)
      - op: "set"
        name: "X-Service-Token"
        from_file:
          path: "/etc/secrets/service-token"
          refresh_interval: "1m"

      # Prepend a static prefix to the file's contents, e.g. "Bearer <token>"
      - op: "set"
        name: "Authorization"
        from_file:
          path: "/etc/secrets/raw-token"
          refresh_interval: "1m"
          prefix: "Bearer "

      # Remove headers added by previous rules
      - op: "remove"
        matching: (?i)^X-Internal-.*

  subgraphs:
    products: # Will only affect the Subgraph named "products"
      request:
        - op: "propagate"
          named: "Subgraph-Secret"
          default: "some-secret"
        - op: "remove"
          named: "X-Custom-Header"
```

### What does the snippet do?

With `all` we address all subgraph requests. Next, we can define several rules on the client's request. The operation `propagate` forwards all matching client request headers to the subgraphs. The operation `set` sets a new header which is forward to the subgraphs. The operation `remove` removes headers that previous rules added to the subgraph request.

The `subgraphs` section allows to propagate headers for specific subgraphs. The name must match with the subgraph name in the Studio.

### Supported header rules

Currently, we support the following header rules:

* **propagate** - Forwards all matching client request headers to the subgraphs. You can choose between one of the following matchers:

  * `named` - It exactly matches on the header name.

  * `matching` - Regex matches on the header name. You can use [regex101.com](https://regex101.com/) to test your regexes. Go to the website and select `Golang` on the left panel. **Note:** The Router *never* propagates [hop-by-hop headers](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers#hop-by-hop_headers) (such as `Connection`) when propagating by regex.

  * `negate_match` - If set to true, the result of the `matching` regex will be inverted. This is useful for simulating negative lookahead behavior, which is not natively supported.

  * `rename`: Replaces the identified header based on its name or matching criteria and transfers the value to the newly specified header.

  * `default`: Fallback to this value when the `named`, `matching` or `rename` header could not be found.

  * `exclude_from_deduplication_key`: Forward the header but leave it out of the request deduplication key. See [Request deduplication](#request-deduplication).

* **set** - Sets a header on the request forward to the subgraph. You must set one of the following:

  * `name` - The name of the header to set

  * `value` - The static value to set for the header

  * `expression` - A [template expression](/router/configuration/template-expressions) that evaluates to the value of the header. For example: `request.auth.isAuthenticated ? request.auth.claims.sub : ''` will set the header to the user's ID if they are authenticated, otherwise an empty string.

  * `from_file` - Source the header value from a file's contents. The file is loaded into memory at startup and re-read on the configured polling interval, so request-time reads never touch disk. Available on request rules only.

    * `path` - Absolute path to the file whose contents become the header value.

    * `refresh_interval` - Determines how often the file is checked for changes and re-read into memory. The minimum value is `100ms`. Defaults to `1m`.

    * `prefix` - A static value prepended to the file's contents. Use it when the file holds a raw token but the header needs a scheme, e.g. `prefix: "Bearer "`. Include any separator, such as a trailing space, in the prefix.

    Use this for mounted secrets that rotate on disk (Kubernetes Secrets, Vault Agent sidecars, externally rotated API keys) without restarting the router.

  * `exclude_from_deduplication_key` - Send the header but leave it out of the request deduplication key. See [Request deduplication](#request-deduplication).

* **remove** - Removes headers from the request forwarded to the subgraph. It only removes headers added by the rules before it. Place it after the rules it should affect. Set exactly one of the following matchers:

  * `named` - It exactly matches on the header name.

  * `matching` - Regex matches on the header name.

  `negate_match` modifies `matching` and requires it. If set to true, the result of the `matching` regex is inverted, so all headers except the matching ones are removed.

<Note>
  Go canonicalizes headers by default e.g. `x-my-header` to `X-My-Header.` Write your rule accordingly or use `(?i)``^X-Test-.*` flags to make your regex case insensitive.
</Note>

### Default value

You can also define a value when the client header is not set by the client. Can only be used with the *named* matcher.

```yaml
headers:
  all:
    request:
      - op: "propagate"
        named: "X-User-Id"
        default: "123"
```

### Request deduplication

The router deduplicates identical in-flight requests to a subgraph ([single flight](/router/configuration#router-engine-configuration)), and identical client requests with inbound request deduplication. Every header a request rule forwards is part of the deduplication key, because two requests with different headers can get different responses. A header that is unique per request, such as a request ID set by your ingress, therefore makes every request unique, and nothing is deduplicated.

Set `exclude_from_deduplication_key` on the rule to keep forwarding such a header while leaving it out of the key:

```yaml
headers:
  all:
    request:
      - op: "propagate"
        named: "Authorization"
      - op: "propagate"
        named: "X-Request-Id"
        # Forwarded to the subgraphs, but requests that differ only
        # in X-Request-Id share one subgraph call
        exclude_from_deduplication_key: true
```

Requests that differ only in excluded headers share one subgraph call, and the subgraph receives the header values of the first of them. Subscriptions that differ only in excluded headers share one subgraph subscription in the same way. A rule with a `matching` regex excludes every header it matches, and a `rename` rule excludes the renamed header.

<Warning>
  Only exclude headers that never change the subgraph response, such as request, correlation or trace IDs. Excluding a header the subgraph uses to build the response, such as `Authorization`, a tenant or a locale, lets one client receive another client's response.
</Warning>

### gRPC services

When using [Cosmo Connect](/connect/overview), headers are forwarded to gRPC services as [metadata](https://grpc.io/docs/guides/metadata/) according to the rules defined in the config.
Metadata keys match header names but in lowercase. To access `X-User-Id` you need to use `x-user-id` as the key.

### Rule ordering

All rules are evaluated in the order they are defined. Rules under `all` are applied before the rules of a specific subgraph. A `remove` rule in `subgraphs` removes headers propagated or set by the `all` rules. A later rule can add a removed header again.

```yaml
headers:
  all:
    request:
      - op: "propagate"
        matching: (?i)^X-.*
  subgraphs:
    products:
      request:
        # Don't forward X-Internal-Token to the "products" subgraph
        - op: "remove"
          named: "X-Internal-Token"
```

  Please inform us if you have more advanced use cases that cannot be accommodated with the current feature set. You can still use [Custom Modules](/router/custom-modules) to implement any logic yourself. You can aggregate or add headers as you like.
</Info>
