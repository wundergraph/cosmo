`@defer` changes when the parts of a response arrive.
It does not change what the response contains.
This page helps you decide whether `@defer` fits a given screen or request.

## Good candidates

- **Fields from a slow subgraph next to fields from a fast one.**
  A product page needs the product name immediately.
  It needs the reviews later.
  If the client defers the reviews, the page renders before the reviews subgraph answers.
- **Content that the user cannot see yet.**
  Data outside the visible area can arrive after the visible data.
- **Expensive computed fields.**
  A field with a `@requires` chain or an expensive resolver adds its latency to the whole response.
  A deferred fragment removes that latency from the initial response.
- **Secondary panels in a dashboard.**
  The primary metrics render first.
  Each secondary panel renders when its fragment arrives.

## @defer compared to split queries

A split of the screen into a fast query and a slow query also delivers the fast data first.
`@defer` differs in these points:

- **One HTTP request.**
  The router plans the deferred fragment together with the rest of the operation.
  It executes them in one HTTP exchange.
- **Shared fetches.**
  The router reuses the entity keys and the parent objects of the initial response for the deferred fragments.
  Two queries fetch them twice.
  [Deferred root fields and fields on non-entity types](/router/defer/how-it-works#deferred-root-fields-in-the-same-subgraph) can still need a second root query.
- **No client-side join.**
  The router tells the client where each fragment belongs through `pending.path` and `subPath`.
  With two queries, the client combines the results itself.
- **Ordering.**
  The initial response always arrives before any deferred fragment.

Two queries remain the better choice in two cases.
The slow data belongs to a different screen.
The client fetches the slow data only after a user action.

## @defer compared to pagination

Pagination reduces the amount of data in a response.
`@defer` changes when the data arrives.
`@defer` does not reduce the data.

- Use pagination when a list is large.
- Use `@defer` when a list is slow but small enough to send in one part.
- Use both when a list is large and slow.
  Paginate the list and defer the first page.

## @defer compared to subscriptions

Both deliver several payloads over one connection.
They solve different problems.

- **`@defer` is a single response that completes.**
  The router delivers every fragment once.
  The router then ends the stream with `hasNext: false`.
  Incremental delivery does not show the changes that happen after the request starts.
- **Subscriptions are open-ended.**
  The router pushes a new payload for every event.
  It continues for as long as the client stays subscribed.

Choose `@defer` when the data is complete after one fetch, and only its arrival time matters.
Choose [subscriptions](/router/subscriptions) when the data keeps changing and the client needs every change.

## Patterns to avoid

- **Deferring fields that the same subgraph returns anyway.**
  A deferred cheap field on the subgraph of its parent adds a second subgraph request.
  The client gains no latency.
- **Deferring fields that the UI needs to render first.**
  The initial response must contain everything that the first view needs.
- **Selecting the same field inside and outside a deferred fragment.**
  The router delivers the field in the initial response.
  The deferred copy has no effect.
- **Deferring small fragments one by one.**
  Each fragment produces its own subgraph requests and its own response part.
  Group the fields that come from the same subgraph into one fragment.

## Checklist

Defer a fragment when the answer to each question is yes.

1. Is the rest of the response faster without this fragment?
2. Can the UI render something useful before the incremental response arrives?
3. Does this screen need the fragment in this request, and not after a user action?
4. Do the fields of the fragment come from a different subgraph than the fields outside it?
5. Do the fields of the fragment have an expensive resolver?
6. Does the client understand a `multipart/mixed` response with `pending`, `incremental`, and `completed`?
